# 振り返りと改善

作業の最後に会話を振り返り、環境 (スキル・ルール・ノート・コード・設定) を改善する。走るたびに環境が良くなる雪だるまのエンジン。この会話で実際に観測されたことにのみ基づく — 推測的な改善は肥大化と副作用を生む。

他スキルの最終ステップとして自律実行されたときは、確認を待たずに進める。DRAFT PR と issue が安全網で、merge は人間が行う。ユーザーと対話中なら、観察と提案の段階で共有して認識合わせをする。

## 観察

良かったことも悪かったことも、判断せずに拾う:

- 失敗・リトライ、回避策・逸脱、非効率・繰り返し現れたパターン
- 情報不足 (足りなかった context、ユーザー確認が必要だった箇所)
- 成功パターン (次の変更で壊さないために明示する)、脆弱な前提
- 成果物の質、ユーザーからの修正指示

## 分析

「なぜ」を繰り返して根本原因まで掘る。会話中の証拠 (エラーメッセージ、実行結果) で裏付け、証拠のない推論は仮説と明記する。症状でなく原因に対処し、1 つの根本原因で複数の症状が消える変更を優先する。

## 反映

学びごとに適切な置き場へ流す。1 つの巨大 PR にせず、意味の単位で独立した PR / 追記に分ける:

| 学びの種類 | 反映先 |
|---|---|
| repo 固有の運用知識 (コマンド、CI の癖、bot) | repo の `.claude/notes/<skill>.md` |
| repo によらないスキルの教訓 | 対象スキルの LESSONS.md |
| 構造的な問題 | スキル・ルール・コードの改善 DRAFT PR |
| 自動化すべき手作業、権限・hook の不足 | settings / hooks の変更提案 |

- 追記だけでなく刈り込む: 古くなった教訓・ルールは消す。モデル更新後は「このルールはまだ必要か」を棚卸しする (不要な指示は性能を下げる)
- 各変更に成功基準を 1 文つける: 次回の run がどうなっていれば成功か
- 観測に基づく改善がなければ「✅ 改善点なし」で終了してよい。無理に作らない

## スキルを変更するとき

- 対象スキルに DESIGN.md があれば先に読む。設計思想に反する変更は改善ではなく劣化
- evals/ があれば、変更後に机上シミュレーションを fresh context で走らせ、通ってから PR にする

## PR

最新の `origin/main` から `improve_{対象}_{短い説明}` ブランチを切り、DRAFT PR を作成する。本文には背景・観測された証拠・成功基準を書き、URL を報告する。
