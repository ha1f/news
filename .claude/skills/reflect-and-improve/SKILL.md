# 振り返りと改善

作業後に会話を振り返り、開発環境（スキル・ルール・コード）を改善するDRAFT PRを作成する。推測的な改善は肥大化と副作用を生むため、この会話で実際に観測されたことにのみ基づく。

> "ask it to self-reflect on what went wrong. This process will help you discover what context Claude actually needs, instead of trying to anticipate it upfront."
> — [Equipping agents for the real world with Agent Skills](https://claude.com/blog/equipping-agents-for-the-real-world-with-agent-skills)

## 手順

### 1. 観察

この会話で行った作業を以下の観点で振り返る。良かったことも悪かったことも、判断せずに拾い上げる。

- **失敗・リトライ**: コマンドの失敗、予期しないレスポンス、やり直しが必要だった箇所
- **回避策・逸脱**: 想定した手順から外れて別の方法で対処した箇所
- **非効率**: 不要な手順、冗長な処理、繰り返し現れたパターン
- **情報不足**: 作業を進めるために足りなかった情報、ユーザーへの確認が必要だった箇所
- **成功パターン**: うまくいったアプローチ。次の変更で壊さないために認識し、他の場面でも再利用できるか検討する
- **脆弱な前提**: 今回はたまたま動いたが、条件が変われば壊れそうな箇所
- **出力品質**: 最終的な成果物の質、ユーザー体験

観察結果をユーザーに共有し、見落としがないか確認する。

### 2. 分析

観察で拾った項目について、根本原因まで掘り下げる。「なぜ？」を繰り返し、構造的な問題を見つける。各段階の回答は会話中の具体的な証拠（エラーメッセージ、実行結果など）で裏付ける。証拠がない推論は仮説と明記する。

例: テストが通ったのにデプロイ後にエラーが出た
→ なぜ？ テスト環境と本番環境で設定が違った
→ なぜ？ 環境固有の設定がハードコードされていた
→ 根本原因: 環境差分を吸収する仕組みがない

### 3. 提案

最もコストパフォーマンスの高い改善を**1件**選び、具体的な変更内容を提案する。改善点がなければ「✅ 改善点なし」と報告して終了。

- **症状でなく原因に対処する**: 根本原因を1つ直すことで複数の症状が消える変更を探す
- **成功パターンを壊さないか確認する**: 観察で見つけた「うまくいったこと」が、この変更で損なわれないか検証する
- **成功基準を述べる**: この改善を適用した場合、次回どうなっていれば成功かを1文で示す

ユーザーに報告し、改善PRを作成するか確認する。

### 4. 改善PRの作成

最新の `origin/main` からブランチ `improve_{対象}_{短い英語の説明}` を作成し、変更をコミット。`gh pr create --draft` でDRAFT PRを作成し、PR本文に背景・変更内容・根拠を含める。PRのURLをユーザーに表示する。
