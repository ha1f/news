# 振り返りと改善

作業の最後に会話を振り返り、環境を改善する。走るたびに環境が良くなる雪だるまのエンジン。この会話で実際に観測されたことにのみ基づく — 推測的な改善は肥大化と副作用を生む。

他スキルの最終ステップとして自律実行されたときは、確認を待たずに進める (DRAFT PR と issue が安全網)。ユーザと対話中なら、観察と提案の段階で認識を合わせる。

## 進め方

1. **観察**: 良かったことも悪かったことも、判断せずに拾う。フレームワークは [references/retrospective-methods.md](references/retrospective-methods.md) から状況に合わせて選ぶ
2. **分析**: 「なぜ」を繰り返して根本原因まで掘る。会話中の証拠 (エラーメッセージ、実行結果) で裏付け、証拠のない推論は仮説と明記する
3. **反映**: 学びごとに最も適切な置き場へ流す。対象のスキルや repo が置き場を定めていれば (教訓ファイル、ノート、ルール等) それに従い、なければ置き場ごと提案する。1 つの巨大 PR にせず、意味の単位で分ける

## 反映の規律

- 症状でなく原因に対処する。1 つの根本原因で複数の症状が消える変更を優先する
- 追記だけでなく刈り込む。古くなった教訓・ルールは消し、モデル更新後は「まだ必要か」を棚卸しする
- 成功パターンを壊さない。各変更に成功基準を 1 文つける (次回どうなっていれば成功か)
- 対象スキルに DESIGN.md や evals があれば従う。設計思想に反する変更は改善ではなく劣化
- 観測に基づく改善がなければ「✅ 改善点なし」で終了する。無理に作らない

## PR

改善は最新の `origin/main` からブランチを切り、DRAFT PR にする。本文に背景・観測された証拠・成功基準を書き、URL を報告する。スキル自体やその教訓ファイルへの反映は、カレント repo でなくそのスキルが配置されている repo へ PR を出す (学びを黙って失わない)。
