# プロンプト改善スキル

`$ARGUMENTS` で指定されたプロンプトを、Anthropic公式のベストプラクティスに基づいて分析・改善する。

公式リファレンス: https://platform.claude.com/docs/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices

## 提示量の原則

メタ説明（診断 + 対応表）の合計分量は、改善版プロンプト本体の分量を超えない。情報を 3 回繰り返すより 1 箇所で正確に書く方が、読み手の負担も少なく原則の汎化も働く。

## ワークフロー

### Step 1: 理解と診断

対象プロンプトを読み、目的と種類を把握する。

**種類の特定:** システムプロンプト / スキル / エージェント指示 / API呼び出し / ルールファイル / ツール記述 のどれか。エージェント向け・出力フォーマット制御・長文コンテキスト・API呼び出しに該当する場合、`references/type-specific-guide.md` の該当セクションを読んでから診断に進む。

**周辺ファイル確認:** ユーザーが「他のルールに基づき」「既存スタイルに揃えて」と明示したり、対象が `.claude/rules/` / `.claude/skills/` 配下のファイルである場合は、同ディレクトリの既存ファイルを Read で開きスタイル要素（frontmatter形式、本文構造、表記慣習）を実際に参照する。CLAUDE.md コンテキストからの推測だけだと、参照根拠が曖昧になり改訂方針がブレる。

**診断観点:** 該当する観点だけを箇条書きで挙げる（網羅性ではなく、改訂につながる発見に集中）。

- **曖昧さ** — 解釈の幅が広い指示。同僚に渡して迷わず実行できるか
- **動機の欠如** — 「なぜそうすべきか」が欠けているか
- **否定形の指示** — 「〜しないで」を「代わりに何をすべきか」に書き換えられるか
- **過剰な強調** — 「MUST」「CRITICAL」「NEVER」「必ず」「絶対」等は Claude 4.5/4.6/4.7 で overtriggering を招く
- **冗長さと重複** — 同じ意味の繰り返し、自明な情報、自己言及
- **構造の不備** — 指示・コンテキスト・入力・出力が整理されているか
- **スコープの曖昧さ** — Claude 4.7 は指示を literal に解釈するため、「全部に適用」「最初だけ」等の範囲明示が必要か

### Step 2: 改善

#### 基本手法

**理由を添える:**
Claudeは理由を理解すると、指示を汎化して想定外のケースにも対応できる。

- Before: `省略記号を使わないでください`
- After: `テキスト読み上げエンジンが省略記号を発音できないため、省略記号は使わずに文を完結させてください`

**肯定文に変換する:**
「何をするか」のほうが「何をしないか」より正確に従える（公式: positive examples > negative）。

- Before: `markdownを使わないでください`
- After: `滑らかに流れる散文の段落で構成してください`

否定形を残す場合は代替手段を併記する（「Don't X — use Y instead」）。

**強調を理由に置き換える:**
強い言葉は過剰反応を招く。理由を添えた通常の表現の方が適切な強度で従う。

- Before: `CRITICAL: You MUST use this tool when...`
- After: `Use this tool when... （直前に理由の説明を配置）`

**冗長さを削る:**
同じ意味の指示は 1 つに統合する。自己言及（「このスキルは〜です」）や空の指示（「がんばってください」「重要です」）は削除する。

**構造を整理する:**
長いプロンプトでは XML タグで指示・コンテキスト・入力・出力を分離する。XML タグの内側では Markdown 強調（`**bold**`）を多用せず、構造はタグで表現する（混在は Claude の構造解釈を曖昧にする）。

**スコープを明示する:**
「全セクションに適用」「最初の一回だけ」「テストを除く全ファイル」のように範囲を具体的に書く。

#### 応用手法

- **例を活用する** — フォーマット・トーン・構造の制御には 3〜5 個の多様な例を `<example>` タグで囲む
- **ロールを設定する** — システムプロンプトの冒頭で専門領域を明示する（「アシスタント」より「Python の型システムに詳しい技術ライティングのレビュアー」）
- **手順指定を緩める** — 細かい思考ステップ指定より一般的な指示の方が推論力を引き出せる。順序が重要なときだけ番号付きで明示
- **過剰なツール促進を抑える** — Claude 4.6/4.7 では「迷ったらツールを使え」が過剰なツール呼び出しを引き起こす

### Step 3: 情報保持の対応表

元プロンプトの全要素と改善版の対応を 1 つの表にまとめる。情報欠落の検証と差分提示を兼ねる。

| 元プロンプトの要素 | 扱い | 説明 |
|---|---|---|
| `具体的な記述` | 保持 / 統合 / 変換 / 削除 / 追加 | 1行 |

扱いの定義:
- **保持** — 文言は変えたが意図そのまま
- **統合** — 別項目とまとめた（統合先を指す）
- **変換** — 否定形→肯定形、強調→理由 など
- **削除** — 自明・冗長・空虚で削除可
- **追加** — 改善版で新規に加えた要素（なぜ必要か）

**「追加」は必ず明示**。新規追加項目（独自の数値基準、推測した技術仕様、想定ユーザー像など）を表に書き落とすと、ユーザーが元由来と提案を区別できない。元プロンプトに根拠がない技術仕様（regex フレーバー、API スキーマ等）を具体化する場合は、断定形を避けて条件付き表現にするか、注記で推測である旨を示す。

### Step 4: 提示

改善版本体と対応表のみを提示する。独立した「変更サマリ」「カテゴリ別変更点」セクションは追加しない（対応表で全てカバーできるため、追加すると重複になる）。対応表の各行が独立した受け入れ単位として読めるように書く。

提示し終えたら最後に分量を確認し、メタ説明が改善版本体を超えていたら対応表または診断を圧縮する。
