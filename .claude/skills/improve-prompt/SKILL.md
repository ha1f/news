# プロンプト改善スキル

`$ARGUMENTS` で指定されたプロンプトを、Anthropic公式のベストプラクティスに基づいて分析・改善する。

公式リファレンス: https://platform.claude.com/docs/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices

## ワークフロー

### Step 1: 理解と診断

対象プロンプトを読み、まず目的と種類を把握する。

**種類の特定:** システムプロンプト / スキル / エージェント指示 / API呼び出し のどれか。
エージェント向け・出力フォーマット制御・長文コンテキスト・API呼び出しに該当する場合、`references/type-specific-guide.md` の該当セクションを読んでから診断に進む。

**診断:** 以下の観点で問題を洗い出す。

1. **曖昧さ**: 解釈の幅が広すぎる指示がないか。同僚に読ませて迷わず実行できるか想像する
2. **動機の欠如**: ルールに「なぜそうすべきか」が欠けていないか
3. **否定形の指示**: 「〜しないで」が、代わりに何をすべきかを示す肯定形に変換できないか
4. **過剰な強調**: 「MUST」「CRITICAL」「NEVER」等の強い言葉がないか
5. **冗長さと重複**: 同じ意味の指示が繰り返されていないか
6. **構造の不備**: 指示・コンテキスト・入力が整理されていないか

### Step 2: 改善

診断結果に基づき改善版を作成する。全てを機械的に適用せず、対象プロンプトの課題に応じて選択する。

#### 基本手法

**理由を添える:**
ルールだけの指示に動機を一文添える。Claudeは理由を理解すると、指示を汎化して想定外のケースにも対応できるようになる。

- Before: `省略記号を使わないでください`
- After: `テキスト読み上げエンジンが省略記号を発音できないため、省略記号は使わずに文を完結させてください`

**肯定文に変換する:**
否定形を「代わりに何をすべきか」の形に書き換える。Claudeは「何をするか」の方が「何をしないか」より正確に従える。

- Before: `markdownを使わないでください`
- After: `滑らかに流れる散文の段落で構成してください`

**強調を理由に置き換える:**
Claude 4.5/4.6は以前のモデルよりシステムプロンプトへの応答性が高く、「MUST」「CRITICAL」等の強い言葉に過剰反応してやりすぎる傾向がある。理由を添えた通常の表現の方が適切な強度で従ってくれる。

- Before: `CRITICAL: You MUST use this tool when...`
- After: `Use this tool when... （直前に理由の説明を配置）`

**冗長さを削る:**
同じ意味の指示が別の表現で繰り返されている場合、1つに統合する。

**構造を整理する:**
長いプロンプトでは、XMLタグで指示・コンテキスト・入力を分離する。一貫したタグ名を使い、階層がある場合はネストする。

#### 応用手法

**例を活用する:**
出力のフォーマット・トーン・構造を制御したい場合、3〜5個の多様な例を `<example>` タグで囲んで提示する。例はClaudeの出力を最も確実に操縦できる手段の一つ。ただし例のバリエーションが偏ると意図しないパターンを学習するため、多様性に注意する。

**ロールを設定する:**
システムプロンプトなら、冒頭でロールを設定する。ロールがあるとClaudeの知識や振る舞いが特定のドメインに集中し、より専門的な回答を返すようになる。

**過剰なツール促進を抑える:**
以前のモデル向けに書かれた「迷ったらツールを使え」等の指示は、Claude 4.6では過剰なツール呼び出しを引き起こす。

**手順指定を緩める:**
思考ステップを細かく指定するより、一般的な指示の方がClaudeの推論能力を引き出せることがある。ただしワークフローの順序が重要な場合は番号付きリストで明示する。

### Step 3: 情報の欠落チェック

プロンプト改善では、簡潔にする過程で元の意図や指示が失われるリスクがある。改善版が出来たら、以下の検証を行う。

1. **全指示の網羅確認**: 元のプロンプトの指示・ルール・制約を一つずつ確認し、改善版のどこでカバーされているかを対応付ける
2. **意図とニュアンスの保持**: 表現を変えた結果、元の意図の強さや範囲が変わっていないか確認する。例えば「絶対に〜しない」を「〜を避ける」に変えた場合、意図の強さが適切かを検討する
3. **例の情報保持**: 元の例を削除・変更した場合、その例が暗黙的に伝えていた情報（エッジケース、期待される判断基準など）が別の形で残っているか
4. **削除・統合の一覧作成**: 削除または統合した項目をリストにし、それぞれについて以下のいずれかを明記する:
   - 改善版のどこでカバーされているか
   - なぜ削除しても問題ないか（冗長だった、起こりえないシナリオだった、等）

欠落が見つかったら、Step 2に戻って改善版に復元する。

### Step 4: 提示

改善前後を比較できる形でユーザーに提示する。

- 変更を分類ごとにまとめる（構造変更 / 表現改善 / 削除 / 追加）
- 各変更に「何を」「なぜ」変えたかの1行説明を添える
- 削除した情報にはStep 3で確認したカバー方法を記載する
- ユーザーが個別の変更を受け入れ・拒否できるよう、独立した変更として提示する
