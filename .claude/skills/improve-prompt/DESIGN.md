# 設計思想

このスキルを改善する前に読む。ここに反する変更は改善ではなく劣化。

## 目的

プロンプトの診断 → 改善 → 受け入れ判断（対応表）→ 検証（eval）までを一貫して提供する。改善版を出して終わりにせず、ユーザーが差分を判断でき、効果を確かめられるところまでが責務。

## 原則

1. 一次ソースは公式ドキュメント。このスキルが持つのは適用の判断基準と手順で、公式の内容はリンクと要点に留める（丸写しは腐る）
2. モデル世代固有の挙動・API 仕様は references/model-notes.md に隔離する。SKILL.md 本文は世代非依存に保ち、世代交代時は model-notes だけ更新する
3. progressive disclosure: SKILL.md は判断と手順の最小集合、詳細は references へ。参照の深さは SKILL.md から 1 段まで
4. 提示の正本は「改善版 + 対応表」。メタ説明が本体を超えない（対応表の「追加」明示とこの上限は実運用の手戻りから生まれた規律。緩める前に経緯を確認）
5. 手作業改善が万能ではない。metric とデータが揃う対象はプログラマティック最適化へ、効果を測りたい変更は eval へ誘導する（誘導先も references に持つ）
6. references の事実（バージョン・数値・仕様）は出典 URL と日付つきで書く（裏取りと更新を可能にする）
7. 正本は 1 箇所。グローバル版 (~/.claude/skills/improve-prompt) と repo 版は同一内容を保つ（分岐すると学びが分かれる）

## 変更するときは

merge 前に [evals/scenarios.md](evals/scenarios.md) の机上シミュレーションを走らせる。棚卸し・刈り込みの規律は reflect-and-improve スキルに従う。
