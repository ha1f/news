# audit

プロダクトと事業をリスク観点ごとに監査する汎用ランナー。観点はスキルに焼き込まず、[audits/](audits/) の監査定義（データ）に置く。誰がいつ走らせても同じ観点・同じ一次情報で監査が再現され、結果が履歴として積み上がる — かつて人にしか投げられなかったチェックを、AI の一次レビューとして繰り返せるようにする仕組み。

監査はその時点の最上位モデル（Fable 系）で実行する（オーナー方針。週次 trigger はモデル指定で従う。手動実行でセッションのモデルが異なる場合は、その旨を成果物に記録する）。

## 監査の選び方

- 引数で監査IDが指定されたらそれを実行する
- 無指定なら、各定義の「再監査トリガー」と「監査履歴」を突合し、条件に該当する監査だけ実行する。該当が無ければ「該当なし」で早期終了する（無理に絞り出さない）

## 実行

監査ごとに fresh context の subagent を起動し、定義ファイルのパスと対象 commit（通常 origin/main の HEAD）を渡す。調査量の多い監査（多数の外部規約の確認など）は、チェックリストの領域単位で複数 subagent に分割して並列化してよい。指示に含める:

- チェックリストの各項目を、一次情報（法令・公式規約・公式ドキュメント）と現物（repo のファイル・公開ページ・実際の出力）の両方で突合し、項目ごとに 適合 / 要修正 / 要判断 / 対象外 の判定と根拠（URL・引用・ファイルパス）を返す
- 前回の監査履歴があれば、前回対象 commit からの差分を中心に見る。全項目を見直すのは、差分が大きいときと定義側が変わったときだけ
- 法的判断を断定しない。解釈が分かれる論点は「要判断」とし、根拠と選択肢を添える。成果物には弁護士等の専門家による助言ではない旨を明記する

## 取捨と反映

レポートを受けて PdM として取捨する。観測された問題・確実な失効だけ拾い、推測的な指摘は捨てる:

- 機械的に直せる要修正 → DRAFT PR にして ready 化
- 判断が要るもの → issue（書式・上限は evaluate-and-triage の新規 issue と同じ。cap 超過時は見送り、監査履歴に残す）
- 人間にしかできない判断（法的リスクの受容・文面の承認・契約） → hold 付き issue / PR に論点を整理して委ねる

## 記録

実行した監査ごとに、定義ファイルの監査履歴表へ1行追記する（日付・対象 commit・結果1行・成果物リンク）。この履歴が次回の差分監査の起点であり、再現性の担保。修正 PR を作った回はそれに同梱し、それ以外の回（issue のみ・全項目適合など）は履歴だけの PR にする。

## カタログの育て方

監査の網羅性は audits/ の成長で決まる。スキル本体でなく定義を育てる:

- 人間に判断を hold で依頼するとき、その判断の観点が既存の定義に無ければ、依頼と同時に定義を追加・更新する。人間の判断は一度きりでも、観点は資産として残り、次回から AI が一次レビューを再現できる（GUARDRAILS の設計原則）
- 新しいリスク面を作る変更（課金・広告・解析・新しいコンテンツ形式）を実装するときは、対応する定義の要否を確認する
- 監査で見えなかった問題が後から見つかったら、その観点をチェックリストに追記する（定義の回帰テスト化）
- 定義自体の陳腐化（法改正・失効した記述・リンク切れ）は audit-and-adopt の資産批評ローテーションが拾う

## 監査定義のフォーマット

audits/{id}.md の構成:

1. **メタ情報**: 監査ID、目的、対象（ファイル・公開ページ・実装）
2. **再監査トリガー**: この監査を再実行すべきイベント・期限
3. **チェックリスト**: 領域ごとの確認項目。各項目に確認方法と一次情報の当たり先を添える
4. **人間に残す判断**: AI が断定・代行してはいけない判断の一覧
5. **監査履歴**: 日付 / 対象 commit / 結果 / 成果物 の表

## 完了条件

- 実行した各監査の指摘が PR / issue / 「該当なし」のいずれかに落ち、監査履歴が追記されている
- hold で人間に委ねるもの以外の PR は ready 化されている
- daily-loop から呼ばれた場合の status issue 記録は呼び出し元（audit-and-adopt）が担う
- 最後に reflect-and-improve を実行する
