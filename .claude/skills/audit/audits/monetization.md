# 収益化準備監査

- **監査ID**: monetization
- **目的**: 収益化（課金・広告いずれの形でも）の前に満たすべき法令・規約・表示の要件を棚卸しし、人間の判断が要る点を「整理された論点」の状態にしておく
- **対象**: references/sources/ の各ソース利用条件、サイトの表示（規約・プライバシーポリシー・運営者情報）、課金・広告・解析の導入計画（VISION.md の M5、docs/m5-paid-delivery.md）

GUARDRAILS は「ソースの利用規約の整理は収益化前に人間が行う」と定める。この監査はその人間の判断を代行せず、判断に必要な材料（各ソースの条件・法令の要件・選択肢）を再現可能に揃える下準備を担う。

## 再監査トリガー

- M5（収益化）の着手前 — 必須
- ニュースソースの追加時（追加分の商用利用条件の確認）
- 広告・アクセス解析・課金手段を導入する PR
- 有料配信の実装 PR（#528 とその後続。設計 docs/m5-paid-delivery.md との整合と、下の「有料配信（メール）導入時の要件」）
- 前回実施から6ヶ月以上経過（ソースの規約は変わる）

### ソース利用条件の棚卸し

- [ ] 全ソース（references/sources/*.md）について、RSS/API の利用規約・商用利用の可否・帰属表示要件を一次情報で確認し、各ソース定義の「利用条件」セクションと [data/monetization-sources.md](data/monetization-sources.md) の詳細（引用・横断整理）を更新する（前回確認日からの差分を見る）
- [ ] AI での処理に対する制限（生成 AI/RAG 利用の除外条項、robots.txt の AI クローラ拒否・Content-Signal）の有無を確認する。明示的に AI 利用を制限するソースは除外を提案する（オーナー方針 #241: AI 不可のソースは使わない。非営利の現状にも効く）
- [ ] 商用利用不可・要許諾のソースを特定し、収益化時の扱いの選択肢（除外・許諾申請・代替ソース）を整理する
- [ ] サードパーティ経由のソース（GitHubTrendingRSS 等）は、経由サービスと元サービスの両方の条件を確認する

### 課金導入時の要件

- [ ] 特定商取引法に基づく表記の要件（事業者名・所在地・連絡先・対価・支払時期・解約条件）を整理し、開示範囲の論点を人間に渡せる形にする
- [ ] 決済プロバイダの利用規約・禁止コンテンツ規定と本サービスの適合を確認する（契約自体は人間）
- [ ] 有料化の範囲と著作権法47条の5への依拠の関係を確認する（legal 監査と併走）
- [ ] 申込画面（配信サービス等の委託先の画面を含む）に、役務の分量（配信頻度・期間）と特商法11条1〜5号の事項（1号 対価・2号 支払時期と方法・3号 提供時期・4号 申込期間の定め・5号 解除に関する事項）と、定期課金なら分量として期間・自動更新の旨・各回と総額が表示され、解約がオンラインで完結するか（特商法12条の6＋消費者庁 通信販売広告Q&A Q21）。サービス選定の必須要件として確認する
- [ ] ポイント・前払い商品を発行せず、対価は決済プロバイダ経由の都度・定期課金に限る前提が維持されているか（資金決済法の登録不要の整理）
- [ ] 価格ページ・申込導線の訴求文（無料期間→有償移行の時期と金額、「公開サイトと重複しない」等の提供内容の説明）が実装と一致しているか（景表法 優良誤認・有利誤認）。課税事業者なら税込の総額表示（消費税法63条）
- [ ] LLM 提供者の規約で、出力の商用利用・サービスの再販禁止の範囲と本サービスの提供形態（読者ごとのキュレーション出力の販売）の関係を確認する（契約の確認は人間）

### 有料配信（メール）導入時の要件

- [ ] 配信サービスの利用規約（禁止コンテンツ・知的財産条項・準拠法）と本サービスの適合を確認し、受信者ごと（またはタグごと）に別の本文を API で送れることを公式ドキュメントで確認する（契約・アカウント開設は人間）
- [ ] 本番に使う送信経路で、テンプレート変数と配信停止リンクが機能し、件名・本文にテスト表示が付かないことを公式ドキュメントで確認する。下書きの試送などプレビュー用の経路は、配信サービスによって件名にテスト表示が付き配信停止リンクが機能しないので、API 上 1 人に送れることだけでは本番の経路にならない（2026-11-01 の履歴）
- [ ] 読者ごとの個人データの所在を棚卸しする: 配信サービス上のメールアドレス、private repo 上の読者ID・購読者ID・関心分野（プロファイル）は照合可能な個人情報データベース等に当たりうる。privacy.md の収集情報・委託先・開示等請求の記述と一致しているか（legal 監査と併走。文面は保護パス）
- [ ] 配信サービスが外国にある場合、個人情報保護法28条の要件（本人同意＋当該外国の制度等の情報提供、または基準適合体制）を申込導線と privacy.md で満たす設計か
- [ ] 配信メールに送信者の氏名又は名称と受信拒否の通知先が表示されるか（特定電子メール法4条。施行規則9条の受信拒否ができる旨・住所・苦情問合せの受付先と、規則7条の表示位置〔受信拒否ができる旨は通知先の直前又は直後〕を含む）。表示事項はメールの中身で変わる: 広告が付随的なだけのメール（規則6条）は4条2号と規則9条の事項が外れて名称だけで足り、お知らせ・プラン案内の同送が広告宣伝そのものに当たるなら全事項と3条のオプトイン・配信停止の導線が要る
- [ ] 有料 run で使うソースが、ソース定義の「商用利用（課金）」の値（`可` のみ。許諾取得後の値は STYLEGUIDE.md に未定義で、使うなら語彙の追加が要る）で機械的に絞られているか。無料テスト配信は非商用の範囲に留まるか

### 広告導入時の要件

- [ ] 景品表示法・ステルスマーケティング規制: 広告と編集コンテンツの区別表示の要件
- [ ] 広告と記事選定の独立性の方針整理（方針決定は GUARDRAILS が人間に留保。論点整理まで）

### 解析導入時の要件

- [ ] 外部送信規律（電気通信事業法）の公表事項の整理
- [ ] プライバシーポリシーの更新要否（legal 監査と併走）

## 人間に残す判断

- 収益化の形の決定と着手判断（VISION.md のフェーズ・マイルストーン判断）
- 決済プロバイダとの契約
- 商用利用不可ソースの除外・許諾申請の判断
- 事業者情報（氏名・住所等）の開示範囲
- 配信サービスの選定と契約（越境移転の整理を含む）、配信メールの送信者表示
