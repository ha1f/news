# 設計思想

このスキルを改善する前に読む。ここに反する変更は改善ではなく劣化。

## 目的

人間の役割を「issue を書く (雑でもよい)・走行中に口を出す・merge する」に縮め、残り全部 (意図の解釈、体制の選択、実装、検証、PR 維持、環境改善) を AI が担う。走るたびに環境が良くなる雪だるまの中核スキル。

## 原則

1. 手順でなくゴールと境界を書く。手順は run ごとにモデルが決める (モデルが賢くなるほど勝手に良くなる設計にする)
2. 主張でなく実行結果が真実。green 条件は機械的に確認できる形で先に決める
3. 曖昧さは orchestrator で止める。worker には確定した仕様だけが届く (これが賢くないモデルでも再現する条件)
4. 書く場所の規律: repo 横断の教訓は LESSONS、repo 固有はスキル内 `notes/` (gitignore 済みローカル保持、どの repo にもコミットしない)、モデル・体制の癖は references/、harness や CLAUDE.md にあることは書かない
5. 短さは機能。1 行足すときは 1 行削れないか考える。数値の規定より判断基準を書く
6. 正本は 1 箇所。repo 横断で使うときはグローバル配置や symlink で共有し、LESSONS は正本にのみ置く (コピーすると学びが分岐する)

## 変更するときは

merge 前に [evals/scenarios.md](evals/scenarios.md) の机上シミュレーションを走らせる。棚卸し・刈り込みの規律は reflect-and-improve スキルに従う。
