# 良い分割の定義

PR 分割と sub-plan の品質基準。原則この基準で練り直してから着手・委譲する。満たせない基準があるとき (不可逆なデータ移行で単体 revert が成立しない等) は、どれをなぜ破るかを計画に明記して進む。

## 良い PR 分割

- 各 PR は単体で意味が通り、単体でビルド・テストが通り、単体で revert できる
- 依存は一方向の鎖にする。相互に依存する 2 つは分割が間違っているサイン (1 つにするか、切る軸を変える)
- 分割の軸は層やファイルでなく「振る舞いの単位」で縦に切る。リファクタと挙動変更は同じ PR に混ぜない
- レビュアーが 1 度に頭に入れられるサイズに収める (目安 400 行以内)
- 並列に走らせる sub-plan 同士は、触るファイルが重ならないように切る。重なるなら直列にするか分割の軸を変える
- 依存鎖の下位 PR を修正したら `git rebase --update-refs` で上位 branch をまとめて restack し、各 PR を常にビルド可能に保つ

## 良い sub-plan

subagent が初見で end-to-end 実装できる自己完結文書。会話の文脈は一切届かない前提で書く:

- 目的 (なぜやるか) と完了条件 (実行できるコマンドと期待結果)
- 対象のファイル・シンボルと、触ってはいけない境界
- 済んでいる設計判断はそのまま渡し、worker に再判断させない。並列 worker 間で共有する命名・API の契約も先に決めて全員に同じものを渡す。逆に裁量に任せる部分はそう明示する
- 返してほしい情報 (変更点の要約、実行した検証とその結果、残った懸念。根拠は file:line 引用で簡潔に)

## 曖昧さは orchestrator で止める

issue や prompt の曖昧さを sub-plan に持ち込まない。調査・判断・質問による曖昧さの解消は orchestrator の仕事で、worker には確定した仕様だけを渡す。worker から「ここが曖昧だった」と返ってきたら、それは分割をやり直すシグナル。
