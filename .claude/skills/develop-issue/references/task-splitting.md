# 良い分割の定義

PR 分割と sub-plan の品質基準。満たせない基準があるとき (不可逆なデータ移行等) は、どれをなぜ破るかを計画に明記して進む。

## PR 分割

- 各 PR は単体で意味が通り、ビルド・テストが通り、revert できる
- 依存は一方向の鎖。相互依存は分割が間違っているサイン
- 層やファイルでなく「振る舞いの単位」で縦に切る。リファクタと挙動変更は混ぜない
- サイズは行数でなくレビューの認知負荷で決める。機械的で均質な変更は大きくてよく、新規実装も分割すると文脈が散るので大きな 1 PR でよい (逸脱の理由は計画に明記)
- diff が大きい原因が commit すべきでないもの (生成物、バイナリ) なら、分割でなく管理方法の改善を提案する
- 並列に走らせてよいのは、依存がなく、触るファイルも重ならない sub-plan だけ
- 依存鎖の下位を修正したら `git rebase --update-refs` で上位をまとめて restack する

## sub-plan

worker が初見で end-to-end 実装できる自己完結文書。会話の文脈は届かない前提で書く:

- 目的と green 条件 (実行できるコマンドと期待結果)
- 対象と、触ってはいけない境界
- 済んだ設計判断と worker 間で共有する契約 (命名・API) は先に決めて渡し、再判断させない。裁量に任せる部分は明示する
- 返してほしい情報 (検証結果と残った懸念。根拠は file:line で簡潔に)
- worker から「曖昧だった」と返ってきたら、分割をやり直すシグナル
