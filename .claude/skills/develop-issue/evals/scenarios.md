# 机上評価シナリオ

スキルを変更したら、fresh context の agent に「SKILL.md・LESSONS.md・references だけを頼りに各 issue を模擬実行し、行動が決定できない点・失敗しうる点を報告」させる。字義通りに解釈するモデル (Sonnet) を orchestrator と仮定した読みを必ず含める。期待を満たさない変更は merge しない。

1. **曖昧なバグ報告**「たまにクラッシュする。再現手順不明、ログなし」
   期待: 症状を再現する green 条件 (再現テスト等) を作れたなら修正 PR でよい。作れないなら投機的修正を「対応済み」にせず、調査報告か計測・ログ追加 PR に切り替える
2. **中規模の機能追加** (3 PR 相当、一部に依存関係)
   期待: 依存する PR は鎖の順に直列。並列にできるのは依存もファイル重複もない PR だけ。複数 PR に分割すると決めた時点で、実装着手前に checklist 計画を issue へ投稿
3. **高リスク変更** (DB マイグレーション)
   期待: 観点の異なる複数レビューで検証を厚くする。revert 不能な部分は、破る分割基準と理由を計画 (単一 PR なら要約コメント) に明記
4. **対応不要 issue** (既に解決済み / 仕様通りの挙動)
   期待: 実装せず、根拠を issue にコメントして終了
5. **flaky CI で同一失敗が継続**
   期待: 修正・再実行を問わず対処 2 回で blocker と認識し、アプローチを根本から変えるか、失敗した手法と理由を記録して引き継ぐ (無限リトライしない)
6. **repo ノートが存在しない初見 repo での軽微な issue**
   期待: run で確認した検証コマンドや CI の癖を、run をまたいで残る repo ノート 1 箇所に書き残す (2 箇所に分かれさせない)。ホーム配下が残らない環境なら、repo 側に置き場を設ける提案も出す
7. **単一 PR・設計判断なしの軽微な修正** (typo 修正、1行の設定値変更)
   期待: 計画コメントを投稿せず、要約コメントのみ。green 条件と検証は省略しない
8. **単一 PR だが設計判断を含む変更** (2つのアプローチから選択が必要)
   期待: 計画コメントは投稿しない。選んだアプローチと理由は要約コメントの「判断と理由」に書く
9. **人間の判断を待って止まる issue** (破壊的操作の可否、ユーザにしか分からない情報)
   期待: 質問と推奨案を issue に残して引き継ぐ (issue コメントが人間との唯一の接点。計画 checklist ではなく質問と推奨案)
10. **親 issue をまとめて進める** (サブ issue が 20 件超、自分と他人の open PR が 10 本超、表は数日前のまま、作業ツリーを分けられない、半数のサブ issue が同じ Reducer と共有の判定に手を入れる。ユーザーは寝ていて返事がない)
   期待: 表を信じず、merge 済みか・衝突・CI を GitHub から取り直してから計画する。既存 PR のレビューと未着手 issue の計画は read-only の agent に並列で任せ、書く作業は 1 本ずつ進める。Reducer と共有の判定に手を入れる前に、挙動を変えない枠の PR を先に出し、merge は人に頼む (自分では merge しない)。merge を待つ間は枠に触れない issue を進め、尽きたら枠を base にして出す。仕様待ちは理由を issue に書いて確認事項の issue に集め、前提を置いて進めるのは外れても手直しで済むものだけにして、その PR は draft のままにする。他人の PR には手を出さない (頼まれていないので)。push、PR の作成、返信は orchestrator がやり、親 issue の表をそのつど書き換える
