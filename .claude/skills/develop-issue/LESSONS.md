# LESSONS

実行から得た repo 横断の教訓。1 教訓 1 行 (理由が必要ならカッコで)。repo 固有の情報はここでなく各 repo のノートへ (置き場は SKILL.md 参照)。repo や git 履歴から分かることは書かない。固有名詞は抽象化する。解消したら消す。

- worktree 環境では diff の base に local branch でなく `origin/<base>` を使う (local が古いと他人の commit が diff に混入する)
- 同一セッションで複数 issue を直列実装するとき、issue 間で `git fetch origin <base>` してから新ブランチを作る (他セッションの push で origin が進んでおり、古い base で作業すると既存コードが見えない。実走でプロファイル記事が見えずビルドが空振りした)
- ユーザ指示で質問をスキップして進むときも、スキップした判断と想定した回答を記録する (issue コメントで人間が後から検証できるように)
- プロンプトに外部サービスの固有名 (bot 名等) をハードコードしない (GitHub API の `user.type == "Bot"` のような型レベルの判定で足りる)
- スキルが対象 repo 自身に置かれている場合、branch を切り替えても開始時に読んだ版に従う (repo 内の別バージョンを読み直すと旧版を実行する事故になる。実走で発生済み)
- issue の具体例は代表例として読む。「〜とか」の周辺にある同種のリスクも確認する
- 実行環境の制約 (ホスティングの plugin 制限等) は一次情報で裏取りしてから技術選定する
- 委譲した内部 skill/agent が同じ「委譲しました、完了したら伝えます」的な空メッセージで完了通知を繰り返す (自己再帰ループ) ときは、2 回目で見切りをつけて TaskStop し、より低レベルな手段 (対象スクリプト/API を直接叩く等) に切り替える
- 大きなコマンド出力はターミナルに直接流さずファイルに出してから読む (出力が重いと途中で切れコンテキストも浪費する。非同期実行なら完了マーカー＋ハンドル ID で結果を取りにいく)
- 既存ファイル (特に共有される基盤コード) の変更は、部分読みの断片でなく差分・正常な先例・コンパイラ/実行の一次情報で裏取りしてから行う (壊れた/古い読み取りに基づく誤変更を防ぐ)
- 環境が高負荷でツール呼び出しが断続的に失敗するときは、1 手番の呼び出し数を絞る (並行呼び出しの連打が失敗を増幅する。read-only 系は通りやすい)
- stack した PR ブランチ間で `commit --amend` する前に `git status` で staged 変更を確認する (別ブランチ用に staged した削除が amend に混入する。実走で2回発生)
- バックグラウンドでビルド/テストが走っている間はブランチ切替・stash をしない (ワーキングツリーが変わり結果が無効になる。停止して commit 済みツリーで再実行する)
- PR の CI 失敗を flake と断定する前に、base を取り込んだツリー (rebase 後 or merge ref 相当) で再現確認する (PR branch 単体の green は base 側の破損を見逃す。実走で誤判定し、真因は base の build 破損だった)
- xcodebuild の `-quiet` は Swift Testing の結果行も消す (exit code でしか判定できなくなる。個別スイートの合否が要る検証では外す)
- issue に添付された一次情報 (デザイン・仕様書) は実装スコープを決める前に全体を確認する。取得手段が失敗してもコード先例や部分情報で代替してスコープを狭めない (実走で画面の主要 UI を見落としてスコープを狭め、実装後に作り直しになった)
- CCR 環境のトリガーは http_api 経由で作成されたものが多く、agent からは update_trigger 不可。トリガーのプロンプト変更で解くより、スキル側のデフォルト動作を変える方が堅牢 (実走で permission denied に遭遇し、スキルのデフォルト変更で解決)
- Playwright の `colorScheme` は browser 直下の `newContext` / `newPage` では効くが、既存 context の `newPage` に渡すと黙って無視される (実走で light のまま撮り、誤った「dark でも問題なし」を出しかけた)
- 検証コードを書いたら、直した挙動を1つずつ元に戻して全て red になるか当てる (正しい入力での green と、壊した入力での red は別の保証。守れていない変更が名指しで出る。実走で7種のうち1種だけが green で生き残った)
- モックは戻り値だけでなく呼び出し引数もアサートする (引数を変える修正は、戻り値だけのモックでは守られない。上の差し戻しで唯一生き残ったのがこれだった)
- 静的サイトの配信用ディレクトリをソースツリー内に作らない (次のビルドがそれを入力として取り込み、生成物が二重になって検査件数が水増しされる。実走でアンカー検査が 2739 → 8217 件に膨らみ、誤った検証結果を PR に書いた)
- 検証スクリプトの出力が想定と違ったら、まず検証器でなく対象を疑う (実走で「数が多すぎる」のをテスト側のセレクタの問題と決めつけて直し、同じ誤りが製品コードにもあることを見落とした)
- 同じ成果物を触る複数の issue を1 run で回すときは、後の branch を先の branch の上に積む (同じ行を両方が書き換えるとコンフリクトが確定する。CI が base=main の PR にしか走らない構成では、スタックした側は base のマージ後に rebase して push するまで検証できない)
- 検証を自分が書き足した行で止めない。書き換えなかった隣接記述との整合と、マージ後に初めて実行される経路まで当てる (実走の1 review run で、隣接する未変更行と正反対の指示になった追記と、マージ後にしか通らない経路のバグが1件ずつ見つかった)
- 消された記述を戻すときは、要約せず元の版と1要素ずつ突き合わせる (落とした1行が、その変更で直そうとしていた欠陥を別経路で作り直す。実走で、誤判定を直す PR が同じ誤判定を fallback 手順に再生産し、レビューで見つかった)
- 生成物の作り方を定める規則を変えたら、規則だけを読ませた fresh context に実物を作らせて確かめる (diff の読み返しでは規則同士の衝突と条件の抜けが見えない。実走で2回とも穴が出て、うち1件は直す対象の失敗が規則の適用条件から外れたままだった)
- 検査ルールは実装前に既存データ全体で精度を測る (一度も発火しない・誤検知だらけのチェッカーは、足しても次から無視される。実走で候補3つを3735件に当てて全て不採用にでき、孤児スクリプトを作らずに済んだ)
- 検証スクリプトは失敗を集計してから出力する (成功メッセージを無条件に print すると、同じ実行の中で「一致」と大量の NG が並び、自分の出力に誤導される)
- 表記のバリエーションを列挙して照合する検査は、要素同士が部分文字列にならない入力でテストする (`9月21日` は `09月21日` の部分文字列になるため、この組をテスト入力に使うと1要素の検査を落としても別要素が代わりに一致し素通りする。`9月5日` と `09月05日` のように互いを含まない組を選ぶ)
- 大量の生成物を一括適用するときは、生成と適用を分け、適用側が書き込む前に機械検証する (担当をまたぐ重複と取りこぼしは統合側にしか見えない)
- 公開する出力 (JSON のキー、生成ファイルの行) は、部品の単体テストでなく出力そのものを見るテストで固定する
- 正本を関数ごと別ファイルから読み込んで使うときは、読み込みに失敗しても主要な出力を止めない設計にする (可用性の伝播を避け、付随的な値だけを欠落として扱う)
