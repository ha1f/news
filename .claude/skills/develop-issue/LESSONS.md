# LESSONS

実行から得た repo 横断の教訓。1 教訓 1 行 (理由が必要ならカッコで)。repo 固有の情報はここでなく各 repo のノートへ (置き場は SKILL.md 参照)。repo や git 履歴から分かることは書かない。固有名詞は抽象化する。解消したら消す。

- worktree 環境では diff の base に local branch でなく `origin/<base>` を使う (local が古いと他人の commit が diff に混入する)
- ユーザ指示で質問をスキップして進むときも、スキップした判断と想定した回答を記録する (issue コメントで人間が後から検証できるように)
- プロンプトに外部サービスの固有名 (bot 名等) をハードコードしない (GitHub API の `user.type == "Bot"` のような型レベルの判定で足りる)
- スキルが対象 repo 自身に置かれている場合、branch を切り替えても開始時に読んだ版に従う (repo 内の別バージョンを読み直すと旧版を実行する事故になる。実走で発生済み)
- issue の具体例は代表例として読む。「〜とか」の周辺にある同種のリスクも確認する
- 実行環境の制約 (ホスティングの plugin 制限等) は一次情報で裏取りしてから技術選定する
- 委譲した内部 skill/agent が同じ「委譲しました、完了したら伝えます」的な空メッセージで完了通知を繰り返す (自己再帰ループ) ときは、2 回目で見切りをつけて TaskStop し、より低レベルな手段 (対象スクリプト/API を直接叩く等) に切り替える
- 大きなコマンド出力はターミナルに直接流さずファイルに出してから読む (出力が重いと途中で切れコンテキストも浪費する。非同期実行なら完了マーカー＋ハンドル ID で結果を取りにいく)
- 既存ファイル (特に共有される基盤コード) の変更は、部分読みの断片でなく差分・正常な先例・コンパイラ/実行の一次情報で裏取りしてから行う (壊れた/古い読み取りに基づく誤変更を防ぐ)
- 環境が高負荷でツール呼び出しが断続的に失敗するときは、1 手番の呼び出し数を絞る (並行呼び出しの連打が失敗を増幅する。read-only 系は通りやすい)
- stack した PR ブランチ間で `commit --amend` する前に `git status` で staged 変更を確認する (別ブランチ用に staged した削除が amend に混入する。実走で2回発生)
- バックグラウンドでビルド/テストが走っている間はブランチ切替・stash をしない (ワーキングツリーが変わり結果が無効になる。停止して commit 済みツリーで再実行する)
- PR の CI 失敗を flake と断定する前に、base を取り込んだツリー (rebase 後 or merge ref 相当) で再現確認する (PR branch 単体の green は base 側の破損を見逃す。実走で誤判定し、真因は base の build 破損だった)
- xcodebuild の `-quiet` は Swift Testing の結果行も消す (exit code でしか判定できなくなる。個別スイートの合否が要る検証では外す)
- issue に添付された一次情報 (デザイン・仕様書) は実装スコープを決める前に全体を確認する。取得手段が失敗してもコード先例や部分情報で代替してスコープを狭めない (実走で画面の主要 UI を見落としてスコープを狭め、実装後に作り直しになった)
- CCR 環境のトリガーは http_api 経由で作成されたものが多く、agent からは update_trigger 不可。トリガーのプロンプト変更で解くより、スキル側のデフォルト動作を変える方が堅牢 (実走で permission denied に遭遇し、スキルのデフォルト変更で解決)
