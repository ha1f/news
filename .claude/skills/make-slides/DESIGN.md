# 設計思想

このスキルを改善する前に読む。ここに反する変更は改善ではなく劣化。

## 目的

聞き手が判断・理解・行動できるデッキを、最初の出力で出す。後から AI っぽさを消したり直したりする工程に頼らず、作る前にそのデッキのルールを確定し、ルールの下で作る。出力形式（pptx、Marp、HTML、Google スライドなど）には依存しない。

## 原則

1. ルールを先に確定する。スライドの作り方は届け方（投影／読み物）と目的（決める／伝える／教える／動かす）で変わり、専門家の意見の対立の多くはこの違いから来ている。モードを決めてから作り、二つのモードの中間を取る折衷はしない。両方に使うデッキは主を一つ決め、もう一方は発表者ノート、アペンディックス、別の文書で満たす
2. 作る基準と確かめる基準を同じにする。各ルールは ID 付きの合格条件を持ち、作るときはそれを満たすように作り、検証では同じ条件を合否で判定する。チェックリストを後付けの修正工程にしない
3. 中身と描画を分ける。設計書（ルールシート、ストーリーライン、タイトル列、スライドごとの設計）は形式に依存せず、描画だけを形式ごとに行う。形式固有の知識は、その形式を扱う既存のスキルやツールに任せ、このスキルには書かない
4. タイトルと図を一組で決める。実証の裏付けがあるのは「主張の見出し＋説明的な図＋少ない文字」の組み合わせと、見出しを伴う対象の強調で、見出しだけの効果は切り分けられていない（どの実験も見出しと同時に図や活字を変えている）。タイトル列の段階で「答える問い・主張・証拠と比較の種類」を一組で書き、検証も一組で行う
5. 根拠の強さを書き分ける。各ルールに出典の略称を付け、実証・規範・経験則を区別する。数値（字数、枚数、pt、色数）はほとんどが経験則で出典ごとに食い違うので、既定値として置き、ユーザーや組織の規定があればそちらを優先する。字数は警告であって制約ではない
6. 全体の点数付けを LLM に任せない。デッキ全体を採点する LLM の評価は人の評価との一致が低い（調査レポートの AI 生成の節）。検査は項目ごとの合否にし、タイトルの通読と描画後の目視は、作った本人ではなく文脈を持たないサブエージェントに任せる
7. 事実を足さない。素材にない数字や事例は作らず「要確認」にして人に返す
8. 例は架空にする（公開 repo のため）。実在の発表やスライドを悪い例として載せない

## 根拠

ルールの出典は [references/sources.md](references/sources.md) にある。調査の全体は repo ルートの `reports/スライド設計とタイトルの原則.md` と `research_notes/スライド設計とタイトルの原則/` にある。ルールを足すときは出典を sources.md に足し、出典のないルールは入れない。
