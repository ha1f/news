# make-slides

聞き手が判断・理解・行動できるデッキを、最初の出力で出す。スライドの作り方は届け方（投影して話すか、読まれるか）と目的（決める・伝える・教える・動かす）で変わる。そこで、作る前にこのデッキのルールを確定し、そのルールの下で作る。できたものから AI っぽさを後で消す工程には頼らない。

## 考え方

以下の手順と合格条件は、次の六つの考え方をこのデッキに当てはめたものである。ルールに書いていない状況と、ルールどうしがぶつかった状況では、ここに戻って決める。考え方の根拠と、ルールにない状況での使い方の例は [references/foundations.md](references/foundations.md) にある。

1. **聞き手の問いに答える。** デッキは、聞き手が見終えた後に判断・理解・行動できるようにするために作る。デッキ全体も各スライドも、聞き手がその時点で抱く問い一つへの答えとして置く。聞き手がまだ問いを持っていなければ、答えの前に問いを作る。載せるか迷った素材は、それで聞き手の判断や理解が変わるかで決める。聞き手には見る条件（画面の大きさ、距離、色覚）も含めて考える。知覚できなければ何も届かない
2. **一番大事な一つは作り手が選ぶ。** 聞き手は最初に目に入った数語と一番目立つものから要点を受け取り、残りは読まないことがある。順位を付けずに並べると、何が持ち帰られるかは偶然で決まる。1 枚につき主張を一つ選んで最初に目に入る場所に置き、ほかの要素はそれを支えるものだけにする。色、大きさ、配置の違いは意味の違いとして読まれるので、意味が違うところでだけ変える
3. **主張は証拠が支える分だけ言う。** タイトルは図や本文を読む枠組みになり、聞き手の記憶はタイトルに引かれる。主張を証拠より強くも曖昧にもしない。証拠の形は主張の種類から決め、証拠がない主張は作らずに人に返す
4. **削るときは消さずに別の層へ移す。** 中身は、タイトル、補足行、図、本文、発表者ノートと口頭、アペンディックス、別の文書に配る。話し手がいれば口頭が層の一つになり、いなければその分をスライドが担う。それがないと主張の真偽や範囲が変わるものは、主張と同じ画面に残す
5. **上流で決まっていないことは下流で直せない。** 何を言うか、どの順で言うか、どう見せるかの順に決める。はみ出しや見た目の問題が出たら、文字を縮める前に、主張が二つ残っていないかを上流で確かめる
6. **届いたかどうかは、文脈を持たない読み手で確かめる。** 作った本人には意図が見えてしまう。聞き手が受け取るものだけを渡し、読み取った内容を書かせて意図と照合する

ぶつかったときの決め方:

- 3 はほかのどれとも引き換えにしない。短さ、言い切り、強調、指定された様式のどれとぶつかっても、証拠以上のことは言わない
- 2 と 4 で迷ったら 1 に戻り、聞き手の問いから決める
- 短く言い切ることと限定を残すことがぶつかったら、主張はタイトルで一つ言い切り、限定は同じ画面の補足行か注記に移す
- 字数、枚数、文字サイズ、色数は、ある画面や場面で 2 と 4 を満たすための目安で、出典ごとに値が違う。その場に合わなければ、数値が守ろうとしている考え方から決める

## 守ること

- 素材にない事実・数字・引用を作らない。足りなければ設計書に「要確認」と印を付けてユーザーに聞く。調べて足すなら出典を付け、それも「要確認」にする。「要確認」は設計書と納品時の報告に書き、描画するスライドには空欄や「要確認」の文字として残さない（その要素は置かずに、人に返す判断に書く）
- 質問や確認（手順 1 の質問、手順 3 の設計書の確認）は聞ける状況でだけ行う。聞けない状況（任せると言われた、無人で実行している、質問できないと言われた）では、返答を質問から始めず、仮定をルールシートに書いて進める
- ルールシートを確定するまでスライドを作らない。途中で聞き手・目的・届け方が変わったらルールシートを書き直し、影響する手順からやり直す。一つのデッキに二つの届け方の密度を載せない（主を決め、もう一方は別の層で満たす。modes.md）
- ユーザーや組織が指定したテンプレート、ブランド規定、社内の資料ルールは references の既定値より優先し、ルールシートに書く。ただし考え方 3 は規定でも曲げない（様式が証拠のない主張を求めるなら「要確認」にして人に返す）
- 描画に汎用のスキルや既定のテンプレート（pptx スキルなど）を使うときも、見た目の判断はルールシートと visuals.md に従う。描画側の推奨（全スライドに視覚要素、丸背景のアイコン、斜体のアクセント、全面のダーク背景など）とぶつかったらこちらを取る
- 不合格を直すときは、その条件だけを通す直し方をしない（T2 を通すために主張を曖昧な 1 語に詰める、T6 を通すために限定を落とす、など）。条件に付いた考え方から直す

## 依頼の範囲

| 依頼 | 行う手順 | 設計書 |
|---|---|---|
| 新しく作る | 1〜7 | ファイルに書く |
| 既存のスライドの一部分（タイトル、図、見た目のどれか）だけを直す・見る。対象は 1〜数枚、見た目だけならデッキ全体でもよい | 下の「部分適用」 | 作らない |
| これから作るデッキの構成やタイトル案の相談 | 1〜3 と、手順 4 のうちタイトルの確定。図・本文の作り込みと描画はしない。判定は D1〜D8 と T | 返答の中に書いてよい |
| 既存のスライドを直す | 下の「既存のスライドを直す・レビューするとき」 | 直す範囲が数枚なら返答の中に書いてよい |
| レビューだけ | 同上。直さずに、不合格の項目と直し方の案を返す | 作らない。判定表は返答に書く |

頼まれた範囲の外に届かない原因があるとき（見た目だけ直してほしいと頼まれたデッキのタイトルがトピック名ばかり、など）は、頼まれた範囲の作業を行い、その原因と直し方の案を納品時に返す。原因は合格条件（T・D 群）で洗い出し、断定せず提案として書く。依頼者が範囲を指定したなら、その判断を尊重する。作業の前に聞くのは、対話できて、かつ範囲を広げないと頼まれた作業自体が無駄になるときだけにする。

## 部分適用

依頼が既存のスライドの一部分（1〜数枚のタイトル、図、見た目のどれか。見た目だけならデッキ全体でもよい）なら、スキル全体を回さずにその部分だけを当てはめる。読む reference は、タイトルなら titles.md と visuals.md の F1 の行、図や見た目なら visuals.md だけにする。考え方は常に効いている。

- ルールシートは作らない。届け方など結果を変える前提だけを読み取り、読み取れなければ仮定する（届け方でタイトルの長さが変わる、など）
- 問い・書き出し・順位は頭の中で行い、返答に書き出さない
- 返すのは、修正案、理由 2〜3 行、人に返す判断（あれば）だけにする。結果を変えた仮定があれば一言添える
- 判定は該当する群（T か F・V）で行い、返答には不合格だった項目だけを書く。タイトルを直すときは、図の形との一致（F1）も見る
- 範囲の外に届かない原因を見つけたら、一言だけ添える（依頼の範囲の節）

## 手順

1. **ルールを確定する**: modes.md を読み、依頼と素材からルールシートを埋める。聞くのは、依頼と素材から決められず、結果を大きく変える項目だけにし、まとめて一度で聞く
   - 届け方と目的は modes.md の見分け方で決め、決められなければ聞く
   - 聞き手は役職と前提知識を確かめる。いまどう考えているか（すでに問いを持っているか）は仮定でも書く。導入の量と結論の位置はこれで決まる
   - 出力形式は描画（手順 5）まで頼まれているときだけ聞く
   - 素材がテーマだけなら、主張したいことと根拠になる事実を同じ質問で聞く。答えがなければ骨組みまで作り、中身は「要確認」にする
   - 聞けない状況では仮定を書いて進める（守ること）。仮定はすべてルールシートに書き、納品時に示す
   - 設計書は plan-template.md のひな形で作り、冒頭にルールシートを書く。ファイルにするなら、ユーザーの指定がなければ成果物と同じ場所（成果物がファイルでなければ作業用の一時ディレクトリ）に置き、納品時に場所を伝える
2. **中核メッセージと素材**: structure.md に従い、デッキ全体の主張を 1 文にし、素材を事実・解釈・行動に仕分ける
3. **骨組みを作る**: structure.md に従ってストーリーラインとタイトル列を設計書に書く。見た目はまだ作らない
   - D1〜D8 を判定し、不合格を直す。D1 の通読は、タイトル列（補足行があれば含む）だけをこのデッキの文脈を持たないサブエージェントに渡し、各スライドに何が載っていそうかとデッキの結論を書かせて、中核メッセージと照合する（サブエージェントを使えない環境では自分で読み、納品時にそう書く）
   - ユーザーと対話できる新規作成なら、ここで設計書（ルールシート、ストーリーライン、タイトル列）を見せ、ずれを直してもらってから手順 4 に進む。任されているなら見せずに進む
4. **1 枚ずつ詰める**: titles.md の手順でタイトルを確定し、visuals.md に従って図を選び、本文と発表者ノートをルールシートの文字量で書く。T 群と、設計書で判定できる F 群（F3〜F6）を判定し、不合格を直す
5. **描画する**: ルールシートの出力形式で描画する。その形式を扱うスキルやツールが使える環境ならそれを使う
   - 描画の前に、テーマ（タイトルの位置、書体、文字サイズ、色、余白）を一度だけ決め、マスターやテーマ定義に置く。各スライドはそこへ中身を流し込み、スライドごとに見た目を考えない。編集できる形式なら、スライドを画像だけにしない
   - 設計書は形式に依存しないので、形式を変えるときは手順 5 からやり直す
6. **検証する**: 全スライドを画像にし、visuals.md の「描画後の確認」に従って V 群、画像で見る F 群（F1・F2）、D9・D10 を判定する
   - 条件の対象外（D5 は決める・伝えるデッキだけ、V1 は投影だけ、など）は「対象外」と書く。画像を作れなかった条件は、設計書や描画データで判定できる範囲で判定し、残りは「未判定」と書く
   - 不合格は該当する手順に戻って直す。直した表現や数字は、デッキ全体（サマリー、アペンディックス、発表者ノート）で同じ箇所を探して揃え、直した箇所を判定し直す
7. **納品する**: 成果物に次を添える
   - ルールシート（仮定したものは仮定と書く）
   - 検証結果。不合格・未判定のまま残したものと、目安から外したものはその理由
   - 人に返す判断（「要確認」の事実、タイトルから外した限定をどこまで残すか、など）

## 既存のスライドを直す・レビューするとき

直す範囲が 1〜数枚の特定の部分（タイトル、図、見た目）なら「部分適用」で行う。それより広いときは、デッキからルールシートを復元する。届け方と目的が読み取れず、それで直し方が変わるなら聞き、変わらないなら仮定を書く。対象のスライドについて titles.md の決め方の手順 1〜3（問い、書き出し、順位）を行ってから判定する（T3 と T7 はこれがないと判定できない）。不合格の項目は手順 2〜5 の該当箇所に戻って直す。部分適用より広い直しでも対象が 1〜数枚なら、判定は D 群を除いた T・F・V にする。
