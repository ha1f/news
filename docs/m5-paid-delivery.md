# M5（収益化）: 有料読者への提供物と配信経路

#522 の成果物。VISION.md の M5「課金の仕組みが動作し、有料読者がフィードを受け取れる」を、現在の構成（GitHub Pages・RSS・日次ループ）で実現する最小構成を決める。2026-10-09 時点の判断で、支払いプロバイダ・価格・規約は人間の決定事項として残す。

## 前提

- 公開サイトは全プロファイル・全日分が GitHub Pages と RSS で誰でも読める。公開済みのものを後から有料にはできない
- 記事本文は転載せず、価値は「選定と導線」にある（`.claude/GUARDRAILS.md` のコンテンツの権利ガードレール）。課金対象は記事ではなく、読者ごとの選定になる
- 日次ループは 1 プロファイルあたり 1 回のキュレーション実行（フィード取得はキャッシュで共有、選定と日本語化が LLM コスト）。プロファイルが増えるとこの実行が線形に増える

## 提供物の候補

| 候補 | 内容 | 現構成で実現できるか | 1 人あたり限界費用 |
|---|---|---|---|
| A. 早期配信・過去分の閲覧 | 公開を遅らせて有料読者が先に読む | 不可。Pages は全員に同時公開で、非公開領域がない | ほぼ 0 だが実現手段がない |
| B. カスタムプロファイル | 読者ごとの `preferences` で選び直したフィード | 可能。既存の `--profile` と publish-pages の仕組みがそのまま使える | キュレーション 1 回分/日（LLM 実行）。最大の費用要因 |
| C. 追加プロファイルの全件 | 既存プリセットを有料側に寄せる | 公開済みなので不可 | 0 |

VISION の「自分の好みで作られた日本語フィード」を課金の対価にするなら B が本線。A・C は公開済みの物を囲えないため採らない。

## 配信経路の候補

| 経路 | 非公開にできるか | 現構成との適合 | 判断 |
|---|---|---|---|
| 1. Pages 上の推測困難な URL（トークン入り RSS） | できない。リポジトリが公開で、URL も共有・漏洩しうる | 高い | 採らない。課金の対価として成立しない |
| 2. 読者ごとの private リポジトリ/Pages | 公開範囲の制御は GitHub Enterprise 契約が要る | 低い | 採らない |
| 3. メール配信（購読管理・課金連携を持つ配信サービス） | できる。受信者ごとに配信 | 中。ループが生成した記事リストをサービスの API に渡す部分を足す | **採用** |
| 4. 認証付きホスティング（Cloudflare Access 等）に有料フィードを置く | できる | 低〜中。Pages 以外に基盤が増える | 3 で足りないときの次案 |

## 採用する最小構成

**カスタムプロファイルの日次フィードを、課金連携のあるメール配信サービスで有料購読者に届ける。** 公開サイトとプリセットフィードは今のまま無料で残す（無料側が集客を担う）。

- 購読管理・決済・解約は配信サービスに任せ、ループは決済情報を持たない
- 有料読者 1 人 = 1 プロファイル。希望の登録は既存のプロファイルリクエスト導線（issue テンプレート）を使う。読者が増えるまでは手動の割り当てで足りる
- 費用は読者数に比例するため、価格は 1 人あたりの日次キュレーション費用を上回るように人間が決める（目安の $1/week は VISION の想定）
- 配信本文は公開フィードと同じく見出し・リード・原文リンクに限る。権利ガードレールの範囲を超えない

## 人間にしかできない判断・作業

1. **ソース利用規約の整理（#241、`hold`）。** 課金（広告でも同じ）の前提。有料化すると商用利用になるため、各ソースの規約を満たすソースだけが有料フィードの材料になる。**これが終わるまで本番課金を始めない**。設計・実装は先行してよい（無料のテスト配信まで）
2. 配信サービスの選定とアカウント開設（課金機能の有無、日本円、手数料、特定商取引法表記の要否）
3. 価格の決定と、利用規約・プライバシーポリシーの改訂（`terms.md`・`privacy.md` は保護パスで人間のマージが必須）。メールアドレスを預かるため privacy.md の更新が要る
4. 事業者としての届出・税務
5. API キーの発行と repo の secrets への登録

## AI ループだけで実装できる部分（切り出す issue）

- 配信用の本文生成: 既存の日次記事（プロファイルの markdown）からメール用の本文（HTML/テキスト）を作る決定的なスクリプトと、そのテスト
- 配信サービスの API に渡す送信スクリプト（`--dry-run` が既定でネットワークに出ない。キーは環境変数）。実送信は人間がキーを登録してから

上の 2 件は順に 1 日で完走できる粒度。issue として別途起票する。workflow の追加は保護パス（`.github/workflows/**`）に当たるため、人間のマージを通る。

## VISION.md との整合

M5 の記述（課金が動作し有料読者がフィードを受け取れる）と食い違わない。VISION.md の更新は不要。
