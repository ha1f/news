# M5（収益化）: 有料読者への提供物と配信経路

#522 の成果物。VISION.md の M5「課金の仕組みが動作し、有料読者がフィードを受け取れる」を、現在の構成（GitHub Pages・RSS・日次ループ）で実現する最小構成を決める。2026-10-10 時点の判断で、支払いプロバイダ・価格・規約は人間の決定事項として残す。

## 前提

- 公開サイトは全プロファイル・全日分が GitHub Pages と RSS で誰でも読める。公開済みのものを後から有料にはできない
- **この repo に入ったものはすべて公開される。** publish-pages はプロファイルの出力を `_posts/{date}-news-{profile}.md` として main に入れ、Pages と RSS に出す。プロファイル定義（`.claude/skills/curate-news/profiles/`）も公開 repo にある。有料の提供物は、定義も出力もこの repo・Pages の外に置く必要がある
- curate-news は repo 外のプロファイルを読める（`--profile path/to/pref.md`）。出力先の `.claude/skills/curate-news/output/` は gitignore 対象で、publish-pages を通さなければ公開されない。2026-10-10 に repo 外のパスを渡して `recent_urls.py`・`recent_topics.py`・`preference_hash.py` が exit 0 で動くことを確認した
- 記事本文は転載せず、価値は「選定と導線」にある（`.claude/GUARDRAILS.md` のコンテンツの権利ガードレール）。課金対象は記事ではなく、読者ごとの選定になる
- **有料フィードは、公開サイトに載った記事と重ならない。** curate-news の重複除外は、直近 7 日の全プロファイルの公開 `_posts/`（`recent_urls.py`）と、過去に公開した URL（`--show-cache-summary`。期間の制限なし）を除外する。そのため有料フィードには、公開サイトに一度でも載った記事は入らない。有料読者にとっては公開サイトとの重複が無いという利点になる。一方で、注目度の高い記事を公開サイトと有料の両方に載せたいなら、有料の run では除外を変える必要がある（下の判断事項に含める）
- 日次ループは 1 プロファイルあたり 1 回のキュレーション実行（フィード取得はキャッシュで共有、選定と日本語化が LLM コスト）。プロファイルが増えるとこの実行が線形に増える

## 提供物の候補

| 候補 | 内容 | 現構成で実現できるか | 1 人あたり限界費用 |
|---|---|---|---|
| A. 早期配信 | 公開サイトより先に有料読者へ届ける | メール経路（下の経路 3）と組み合わせれば可能 | ほぼ 0（同じ記事を早く送るだけ） |
| B. 非公開のカスタムプロファイル | 読者ごとの好みで選び直したフィードを、本人にだけ届ける | 可能。curate-news を repo 外のプロファイルで走らせ、publish-pages を通さずに出力を配信に回す | キュレーション 1 回分/日（LLM 実行）。最大の費用要因 |
| C. 既存プリセットの有料化 | 公開中のプロファイルを有料側に移す | 過去分は公開済みで囲えない | 0 |
| D. 関心ごとの非公開フィード（共有） | 関心ごとのフィードを、そのフィードを選んだ購読者全員に同じ本文で届ける | 可能。B と同じく repo 外のプロファイルで走らせる。日次手順はフィード単位にする（#613） | キュレーション 1 回分/日 ÷ 購読者数 |

**B を本線にする。** VISION の「自分の好みで作られた日本語フィード」をそのまま対価にでき、公開サイトとの差（自分専用であること・他人に見えないこと）が明確になる。2026-10-28 に、D をプレミアムフィード、B を完全パーソナライズとする 2 tier にした（下の「有料の tier と費用を下げる方針」）。

A は採らない。日次のニュースで公開を数時間遅らせても読者が得るものが小さく、遅らせた分だけ無料の公開サイト（集客を担う側）の鮮度が落ちる。C は公開済みの物を囲えないため採らない。

## 配信経路の候補

1 人あたり限界費用は、読者が 1 人増えたときに増える費用。ここでは配信と決済の費用を見る（キュレーションの費用は提供物 B の行に計上済み）。決済は国内カードを想定し、Stripe の公開料金（2026-10-10 に [stripe.com/jp/pricing](https://stripe.com/jp/pricing) で確認: 国内カード 3.6%、定期課金の Billing は取引額の 0.7%）を基準にする。

| 経路 | 非公開にできるか | 現構成との適合 | 1 人あたり限界費用（配信 + 決済） | 判断 |
|---|---|---|---|---|
| 1. Pages 上の推測困難な URL（トークン入り RSS） | できない。repo が公開で、生成物も Pages に載る。URL も共有・漏洩しうる | 高い | 配信 0 + 決済 約 4.3% | 採らない。課金の対価として成立しない |
| 2. 読者ごとの private repo の Pages | 閲覧者の制御（private Pages）は GitHub Enterprise Cloud が要る | 低い | Enterprise の席単価が読者数に比例して乗る | 採らない |
| 3. メール配信（購読管理・課金連携を持つ配信サービス） | できる。受信者ごとに配信 | 中。ループの出力をサービスの API に渡す部分を足す | 下の内訳を参照。手数料率型で売上の約 4〜15%、または固定費型で限界ほぼ 0 | **採用** |
| 4. 認証付きホスティング（Cloudflare Access 等）に有料フィードを置く | できる | 低〜中。Pages 以外に基盤が増え、置き場とアクセス管理を新しく持つ | ホスティング自体は小さいが、認証の席単価が乗るサービスがある + 決済 約 4.3% | 3 で足りないときの次案 |

経路 3 の費用はサービスの課金モデルで二つに分かれる（いずれも 2026-10-10 時点。選定時に人間が一次情報で当て直す）:

- **固定費型**（例: Buttondown。[料金ページ](https://buttondown.com/pricing)で購読者 100 人まで無料、有料購読の機能は月 $9 の追加。有料購読への手数料の記載なし）: 1 人あたりの限界費用は決済手数料（約 4.3%）だけ。ただし固定費（月 $9 と、購読者の段階ごとの料金）があるので、読者が少ないうちは 1 人あたりの平均費用が重い
- **手数料率型**（例: Substack は有料購読の売上の 10% と決済手数料を取る。公式ページは取得できず、複数の第三者の解説で一致した値）: 1 人あたり売上の約 13〜15%。固定費は無い

**サービスの必須要件: 受信者ごと（またはタグ・セグメントごと）に別の本文を API で送れること。** 提供物 B は読者ごとに中身が違うので、1 号を全購読者に同じ本文で送る形しか持たないサービスは使えない。どちらの型でもこの要件を満たすかを先に確かめる。あわせて、申込画面に役務の分量（配信頻度・期間）と対価・支払時期と方法・提供時期・自動更新の旨と解約条件が表示でき、解約がオンラインで完結することも選定の必須要件にする（配信サービスの申込画面は特定商取引法 12 条の 6 の「委託を受けた者」の手続に当たりうる。消費者庁 通信販売広告 Q&A の Q21 は、解約通知が無い限り続く契約ではその旨と各回の対価の表示を求める）。

## 採用する最小構成

**非公開のカスタムプロファイルの日次フィードを、課金連携のあるメール配信サービスで有料購読者に届ける。** 公開サイトとプリセットフィードは今のまま無料で残す（無料側が集客を担う）。

- **有料プロファイルの定義と出力は公開 repo・Pages に出さない。** 定義は人間が作る private repo（例: `ha1f/news-paid`）に置く。日次ループはそれを**公開 repo の作業ツリーの外に** clone し（中に置くと、publish-pages の `ls profiles/*.md` が拾って公開する経路や、公開 repo の `git add` に巻き込まれる経路ができる）、curate-news に `--profile <private repo 内のパス>` で渡して走らせる。出力は gitignore 対象の `output/` に出し、publish-pages は通さず、そのまま配信の本文生成に渡す。公開 repo には有料プロファイルの名前も中身も残らない
- **公開 repo への書き込み経路にも中身を出さない。** 有料の run は status issue へのコメント・reflect-and-improve の PR・issue コメントなど、公開 repo に書く経路を持つ。そこには件数と成否だけを書き、プロファイルの関心・見出し・URL は書かない。reflect-and-improve を呼ぶなら、証拠の引用を伏せることを有料の手順に明記する
- **プロファイルが取れないときは送らずに止める。** clone に失敗してファイルが無いと、`preference_hash.py` は `default` を返し、curate-news は汎用フィードを作る。そのまま送ると、全読者に汎用フィードが黙って届く。また出力のファイル名はプロファイル内容のハッシュなので、プロファイルを編集すると重複除外の履歴が切れ、中身が同じ読者どうしでは出力が衝突する。有料の手順は、プロファイルの存在を確かめてから走らせ、出力は読者 ID で区別する
- **出力の保管先も private repo にする。** 実行環境はセッションごとに作り直されるため、`output/` は run をまたいで残らない。curate-news の重複除外（`recent_urls.py` が過去 7 日の `output/` を見る）を有料フィードでも効かせるには、送信済みの出力を private repo に保存し、次の run で `output/` に戻す必要がある
- **有料 run で使うソースは、ソース定義の「商用利用（課金）」の値で機械的に絞る**（値が `可` のソースに限る。語彙は curate-news の STYLEGUIDE.md の `可 / 不可 / 要許諾 / 要連絡 / 要判断 / 規定なし` で、許諾を取得した後の値は未定義。許諾済みのソースを使うなら、先に STYLEGUIDE.md へ語彙を足す）。curate-news は既定で全ソースを読むため、#241 の結論が出ても適用先が無いと、商用不可のソース（2026-10-11 時点で 18 ソース中、不可 5・要許諾 4・要連絡 1）が有料フィードに入る。無料のテスト配信はこの制限を掛けない（実装済み: `fetch_feeds.py --paid`。#575）
- 購読管理・決済・解約は配信サービスに任せ、ループは決済情報を持たない
- 完全パーソナライズ（提供物 B）は、有料読者 1 人 = 1 プロファイル。プレミアムフィード（提供物 D）は 1 フィード = 1 プロファイルで、購読者は配信サービスのタグ（またはセグメント）でフィードに結び付ける（#613）。読者 ID・受信先（配信サービスの購読者 ID）・プロファイルのファイルの対応表は private repo に置き、送信スクリプトはこれを入力にする（メールアドレスそのものは配信サービスに持たせ、repo には置かない）。**希望（関心分野）は配信サービスの登録フォームで受け付け、公開の GitHub issue では受け付けない。** 支払った人の GitHub アカウントと関心が公開されるのを避けるため。フォームの内容から private repo のプロファイルを作るのは、読者が増えるまで人間の手作業で足りる
- 価格は tier ごとに、1 人あたりの原価と配信・決済の費用を上回るように人間が決める（目安の $1/week は VISION の想定）。1 人あたりの原価は、プレミアムフィードなら 1 本の日次キュレーション費用 ÷ 購読者数、完全パーソナライズなら 1 人 1 本分。キュレーション費用の実測は下の「キュレーション費用の実測」節（#592）
- 配信本文は公開フィードと同じく見出し・リード・原文リンクに限る。権利ガードレールの範囲を超えない

## 有料の tier と費用を下げる方針（2026-10-28 オーナー判断）

上の最小構成（提供物 B を読者ごとに Opus で回す）では、読者 1 人あたりの原価が約 $7.3〜8/週になる（下の「curate-news 1 回の実測」）。オーナーはこれを売れない価格と判断し、次の前提で作ることにした。

- **品質は下げない。** 選定と日本語化の質が、このサービスと他のニュースサイトとの差。選定と書く工程は Opus に残し、モデルを丸ごと Sonnet・Haiku にする手は採らない（下の「Opus と Sonnet の品質比較」、#609）
- **課金を 2 つの tier に分ける。**

| tier | 中身 | 1 人あたりの原価 | 人が増えたとき |
|---|---|---|---|
| プレミアムフィード（提供物 D） | 関心ごとのフィードを、そのフィードを選んだ購読者全員に同じ本文で届ける | 1 本の日次 run（Opus で約 $7.3〜8/週）÷ 購読者数 | 購読者数に反比例して下がる |
| 完全パーソナライズ（提供物 B） | 読者ごとのプロファイルで作る | 1 人 1 本分 | 下の 2 を入れれば、ほかのフィードと選ぶ記事が重なる分だけ下がる |

- **費用を下げる手を組み合わせる。** どれも Opus の品質を保つ手。効きは #612 で測る:
  1. **フィードを共有する。** プレミアムフィードの tier そのもの。日次手順をフィード単位にする（#613）
  2. **記事ごとの作業を共有する。** 見出しと読みどころの大半は記事について書く文章で、読者によって変わらない（curate-news の手順5「読んだら何がわかるか」）。同じ日に複数のフィードが同じ記事を選んだら、本文の取得・事実の確認・見出しと読みどころは 1 回にして使い回し、フィードごとには選定とリードだけを回す。ただし続報表記（「続報（M/D掲載）。」はそのフィードの掲載履歴で決まる。#559）と、その日はじめて出す固有名詞の説明（フィード内の並びで決まる）はフィードごとに変わるので、共有した文をフィードごとに調整する。VISION.md の M2 は「取得・要約などの共通処理は全プロファイルで1回に保つ」を方針とし、完了判定にも「共通処理（取得・要約）は1回」と書いているが、実際に共有しているのは取得だけで、読みどころ（要約にあたる部分）はフィードごとに書いている。これを方針どおりにする形になる（VISION の完了判定の記述は、#612 の計測で実態を確かめてから直す）。公開フィードの日次 run にも効く
  3. **読む量の多い工程を Sonnet に任せる。** 下の「Opus と Sonnet の品質比較」（#609）で差が出たのは、選定より日本語化だった。工程の分け方の初期案を次に置く。オーナーが決めたのは「読む量の多い工程だけを Sonnet に任せる」までで、表の割り当ては #612 で費用と品質を測ってから確定する（事実の抜き出しを Sonnet に任せる行の懸念は下の「未確認の点」）

| 工程 | 担当 | 理由 |
|---|---|---|
| ソース選択・候補を数十件に絞る | Sonnet | 読む量が最も多い。拾い漏れを避けて多めに残す |
| 記事本文の取得と事実の抜き出し | Sonnet | 読む量は多く、判断は小さい。根拠の箇所を添えたメモにして、Opus が確かめられるようにする |
| 最終選定（セレンディピティ枠を含む） | Opus | 何を載せるかがサービスの価値 |
| 見出し・読みどころ・リード | Opus | #609 で差が出た工程 |
| ファイル作成・形式の検査 | Sonnet | 機械的 |

**効きの見込み（未測定）。** Sonnet 5.5 の単価は入力・出力とも Opus 5.5 の半分（100 万トークンあたり入力 $2・出力 $10。Opus は $4・$20。2026-10-06 時点の公開価格）だが、キャッシュの読み直しはどちらも $0.20 で同じ。3 で下がるのは、新しく読み込む分と書く分、それに Opus の文脈が小さくなって読み直しが減る分になる。A（Opus・直接）の内訳をこの単価で分けた粗い見積もりで、1 本 $1.04/日が $0.7 前後（週 $5 前後）になる。前提は、A の文脈（約 12 万トークン）のうち候補と記事本文にあたる約 8 万を Sonnet が読み、Opus は Sonnet のメモを含めて約 4 万の文脈で選定と執筆をすること。プレミアムフィードなら、$1/週で原価を回収できる購読者数が 1 本あたり 8〜9 人から 5〜6 人に下がる（配信・決済の費用は別）。2 の効きは、工程別の費用と、フィードどうしで選ぶ記事がどれだけ重なるかで決まる。

**未確認の点**

- 工程別の費用（選定と記事ごとの作業がそれぞれいくらか）と、3 の形の費用と品質（#612）。事実の抜き出しを Sonnet に任せると、#609 で Sonnet に出た事実の誤りがメモ経由で入りうる
- 有料に使えるソースは 2026-10-28 時点で 0 本（商用利用（課金）が `可` のソースが無い。#241 待ち）。使えるソースの数と顔ぶれで、作れるプレミアムフィードの本数と品質が決まる

## キュレーション費用の実測（#592）

提供物 B の最大の費用要因である「読者 1 人ぶんのフィードを 1 日 1 回作る費用」を、公開プリセットの日次 publish（`毎日ニュース` trigger の run）から測る。有料プロファイルの run は測っていない（まだ存在しない）。

### 測り方

`毎日ニュース` の 1 run は、メイン（`preferences.md`）とプロファイル 4 本（`profiles/*.md`）の計 5 フィードを作る。publish-pages はフィードごとに subagent を 1 つ起動して curate-news を回し（取得・選定・日本語化）、オーケストレータが投稿ファイルの作成・検査・PR 作成・振り返りを行う。

- **run 全体の費用は取れる。** Claude Code Remote の `get_session` が返す `external_metadata.usage.cost_usd` を読む。トークン数（`input_tokens`・`output_tokens`・`cache_read_tokens`・`cache_write_tokens`）も同じ場所にある
- **フィード別・共通処理別の内訳は取れない。** `get_session` はセッション単位の合計しか返さず、subagent ごとの使用量は出ない。subagent の分は `cost_usd` に含まれる（下の「curate-news 1 回の実測」で確認。#601）
- **代わりに使う推定: 1 フィードあたり = run 全体 ÷ 5。** フィードの取得はキャッシュで共有されるが、LLM の費用はフィードごとの選定・日本語化（subagent）と、フィードごとの投稿ファイル作成・検査（オーケストレータ）に掛かり、ほぼフィード数に比例する。共通処理（ブランチ・PR 作成、振り返り）も 5 等分に含むが、下の「curate-news 1 回の実測」では curate-news 1 回の費用 × 5 が run 全体と同じか少し大きく、共通処理の大きさは測れなかった（フィードごとの差に埋もれる程度）。÷5 は 1 フィードの費用の近似として使えるが、上限とは言えない。有料の日次手順は publish-pages を通さず、読者ごとに curate-news と本文生成・送信を回すだけなので、読者 1 人の追加費用は「curate-news 1 回」に近い
- `cost_usd` は API の従量料金に換算した値。定額プランで回している間は、実際の支払いはプランの料金で、この値は「同じ処理を API で回したときの費用」と読む。有料化で読者が増えると定額プランの上限に当たるので、価格はこの換算値で考える

### Opus と Sonnet の品質比較（2026-10-28、#609）

公開プリセット `engineer` の curate-news を、同じ取得結果から Opus と Sonnet でそれぞれ 1 回、委譲の形（形 B・D と同じく subagent 1 つに curate-news を任せる）で回し、出力を比べた。

**揃えた条件。** 全ソースを 1 回だけ取得し（reddit-swift と reddit-MachineLearning は HTTP 429 で取得できず、両方とも欠けたまま）、そのキャッシュを main から切った 2 つの git worktree に複写して、各 worktree で subagent を 1 つずつ同時に起動した。取得目的の `fetch_feeds.py` を禁じ（キャッシュの無いソースは fallback せずスキップ）、終了後にキャッシュが両方とも取得時と一致する（sha256）ことを確かめた。日付は両方 2026-10-28、push・`_posts/` への書き込みはしていない。記事ページの取得（`fetch_article_context.py`）は手順どおり許した。

### 再現手順

1. その日の publish の session ID を、main の curation commit の trailer から取る（squash で他の commit の trailer も並ぶので、最初の 1 行を使う）:
   ```bash
   git fetch origin main
   git log origin/main -1 --grep "Add news curation for YYYY-MM-DD" --format=%b | grep -m1 Claude-Session
   ```
   当日分なら `list_triggers` の `毎日ニュース` の `last_run.session_id`（`cse_` を `session_` に読み替える）でもよい
2. Claude Code Remote の MCP で `get_session(session_id)` を呼び、`title` が `⚡ 毎日ニュース`・`created_at` がその日の 00 時台（UTC）であることを確かめてから、`external_metadata.usage.cost_usd` と `external_metadata.last_served_model` を読む
3. その日のフィード数を数え（`git ls-tree --name-only origin/main _posts/ | grep -c 'YYYY-MM-DD-news'`）、run 全体の費用をそれで割り、7 を掛けて週あたりにする

curate-news 1 回の費用（上の「curate-news 1 回の実測」）は、Claude Code Remote の `create_session` で `/curate-news --profile <公開プリセット名>` を回す別セッションを立て（`append_system_prompt` で commit・push・コメント・reflect-and-improve を禁じる）、`get_session` の `session_status` が `SESSION_STATUS_IDLE` になってから同じく `usage` を読む。`post_turn_summary` で出力を書き終えたか（途中で止まっていないか）を確かめる。

モデル間の品質比較（上の「Opus と Sonnet の品質比較」）は、1 セッションの中で行う: `fetch_feeds.py`（引数なしで全ソース）を 1 回回し、`git worktree add --detach` で作った 2 つの worktree に `.claude/skills/curate-news/cache/*.json` を複写して sha256 を控える。Agent ツールで `model` を変えた subagent を各 worktree に 1 つずつ同時に起動し、取得目的の `fetch_feeds.py`・commit・push・`_posts/` への書き込みを禁じて curate-news を回させる。終わったらキャッシュの sha256 が変わっていないことと、subagent transcript の `model` がすべて指定どおりであることを確かめ、出力をモデル名を伏せて fresh context の subagent に検査させる。トピック重複は検査役に掲載履歴が無いので `recent_topics.py --profile <名前>` で別に確かめる。

記録に載せるのは公開プリセットの run の session ID と数値だけにする。有料プロファイルの run を測るときは、プロファイルの中身・見出し・URL を書かず、費用と件数だけを書く。

- **無料との重なりは、取得5日分では候補ごとの差が小さい。** security は 11-05・11-07 は最も低かった（6%・13%）が、11-08 は26%で記録のある3候補のうち最も高く（ai-build 19%・apple-mobile 22%）、11-09 も23%で ai-build（30%）・apple-mobile（33%）と大差ない。「security が無料と重なりにくい」とは今の幅では言えない
- **#241 の許諾の効き方。** 2026-11-05 時点で値が `可` のソースは 0 本なので、どの候補も今は有料で回せない。security の未公開の材料は hatena・itmedia（どちらも要許諾）が多い（11-05 は未公開32本中22本、11-07 は27本中15本、11-09 は24本中12本）。ただし hatena 経由の記事は元の媒体（日経は不可など）の扱いが別で、hatena の許諾だけでは使えない記事が残る。apple-mobile は規定なしのソース（zenn・gigazine）と要許諾（itmedia・qiita）が混ざる。ai-build は規定なし（zenn・infoq・hackernews）が目立つが、不可・要連絡・要許諾も混ざり、過半ではない
- **暫定の推奨は security（取得5日分での判断。1〜2週の取得で見直す）。** 根拠は「無料に対応するフィードが無い」ことだけで、これは日によらない。量（日曜の 11-08 は3本）と重なり（4〜26%）は、5日分では ai-build・apple-mobile より有利とは言えない。日曜・週末の本数が続けて10本を割るなら、平日だけ配信するか ai-build に回すことを考える。材料の半分前後が要許諾の2社なので、許諾が取れなければ apple-mobile か ai-build に回る。決定はオーナー

この文書が review を通ってから、#522 から切り出して起票する（設計が固まる前に実装の issue を置くと、作り直しになるコードが先に作られるため。2026-10-10 のグルーミングで、旧構成を前提にした #523・#524 は #522 に統合して close 済み）。

- **配信用の本文生成**（実装済み: `.claude/scripts/render_email_body.py`、#528 / PR #541）: curate-news の出力（`output/` 配下。`_posts/` ではない）からメール用の本文（HTML/テキスト）を作る決定的なスクリプトと、そのテスト。入力も出力も公開 repo にコミットしない
- **送信スクリプト**（実装済み: `.claude/scripts/send_email.py`、#555 / PR #556。配信サービスは Buttondown を仮置き）: 配信サービスの API に本文を渡す（`--dry-run` が既定でネットワークに出ない。キーは環境変数）。実送信は人間がサービスを選び、キーを登録してから。1 人にだけ送る経路は公式 OpenAPI で裏が取れるものに限る（Buttondown では `status: draft` で作って `POST /v1/emails/{id}/send-draft` に購読者 ID を渡す。`status: transactional` は API changelog 2025-04-17 では表示用の値で、`/v1/subscribers/{id}/emails/{email_id}` は finalized なメール専用。2026-10-18 の monetization 監査で修正）。ただし send-draft は公式 docs 上「下書きをレビュー用に送る」機能で、有料読者への本番配信に使えるか（下書き表示が付かないか、配信停止リンクとフッタが付くか、配信記録に残るか）は未確認。初回の実送信は、オーナーだけが購読するテスト用ニュースレターで draft のまま作られること・本人にだけ届くこと・下書き表示が無いこと・配信停止リンクが付くこと（本文の `{{ unsubscribe_url }}` が本人用の有効なリンクに展開され、配信サービス自身のフッタと二重にならないこと）を確かめてから行う。使えなければ経路を選び直す
- **有料フィードの日次手順**: private repo の対応表の読者ごとに、プロファイルの存在確認 → curate-news → 本文生成 → 送信 → 出力の private repo への保存、を回すスキル側の手順。公開 repo の `_posts/` と Pages に何も出ないこと、status issue などへの書き込みに件数と成否しか載らないことを検査で確かめる（実装済み: 下の「日次手順」と `.claude/scripts/paid_daily.py`。#582）

いずれも 1 日で完走できる粒度。上から順に依存する（3 つ目は private repo の作成を待つ）。workflow の追加が要る場合は保護パス（`.github/workflows/**`）に当たるため、人間のマージを通る。

2026-10-28 の tier と費用の方針（上の「有料の tier と費用を下げる方針」）で、次を足した:

- **費用を下げる手の計測**（#612）: 工程別の費用、読む工程を Sonnet・選定と書く工程を Opus にした形の費用と品質、同じ日のフィードどうしで重なる記事の本数を測り、tier ごとの見込みを更新する
- **プレミアムフィードの日次手順**（#613）: フィードの対応表から、フィード単位で curate-news を 1 回回し、履歴もフィード単位で持ち、購読者のタグ（またはセグメント）へ一斉配信する
- **記事ごとの作業の共有**（#612 の結果を見てから起票）: curate-news を、記事ごとの作業（本文の取得・事実の確認・見出しと読みどころ）を日付単位で 1 回にまとめる形に分ける。公開フィードの publish-pages も同じ仕組みに乗せる

#612 と #613 は互いに依存しない。

## 日次手順

有料フィードの run は、次の順で読者を1人ずつ回す（並列にしない。同じ内容のプロファイルを持つ読者どうしは curate-news の出力ファイル名が同じになる）。決定的な部分は `.claude/scripts/paid_daily.py` が持ち、curate-news（LLM の選定）はその間に挟む。`ROOT_DIR` は private repo を clone した先で、公開 repo の作業ツリーの外に置く（中にある・作業ツリーを含む、のどちらも `paid_daily.py` が拒否する）。

`ROOT_DIR` の構成:

- `readers.json`: `[{"reader_id": "r-001", "subscriber_id": "<配信サービスの購読者 ID>", "profile": "profiles/r-001.md"}]`。`reader_id` は英数字・`_`・`-`（数字だけは不可）。`profile` は `ROOT_DIR` からの相対パスで、`ROOT_DIR` の外や公開 repo の中は指せない。公開フィードのプロファイル（`preferences.md`・`profiles/*.md`）と同じ内容のものは拒否する（出力ファイル名のハッシュが重なり、公開フィードの重複除外の履歴を書き換えるため）。メールアドレスは置かない
- `footer.json`: メール本文の末尾に入れる送信者の名称と配信停止の案内（特定電子メール法 4 条の表示。#595）。`{"sender": "<送信者の氏名又は名称>", "unsubscribe_url": "{{ unsubscribe_url }}", "lines": ["<住所>", "<問い合わせ先>"]}`。`unsubscribe_url` は https の URL か、配信サービスが購読者ごとに差し込む配信停止リンクの変数（Buttondown の `{{ unsubscribe_url }}`。他の変数名は書き間違いとして拒否する）。`lines` は任意の追加行。文面はオーナーが決めて private repo に置き、公開 repo には置かない。無い・空・形式が違うと `finalize --send` は送らない（`send_email.py --send` も、フッタの無い本文は送らない）
- `sent/{reader_id}/{日付}.md`: 送信済みの出力。`finalize --send` が書く。`{日付}.sending` は送信中の印で、届いたか分からない失敗（通信の例外）のときに残る。残っている読者には同じ日の分を送らないので、配信サービス側で届いたか確かめてから人が消す

読者ごとに:

1. `python3 .claude/scripts/paid_daily.py prepare --root ROOT_DIR --date YYYY-MM-DD --reader ID` — プロファイルを確かめ、最初の読者のときは run の起点として HEAD を記録し、`sent/` の直近14日分を `output/` に戻し（curate-news の重複除外がその読者の履歴で効く）、当日の出力を消す。プロファイルが無い・読めない・空なら非0で終わる。**その読者は curate-news に進めない**（`preference_hash.py` が `default` を返し、汎用フィードを作る経路に入る）
2. curate-news を、prepare が表示した `--profile <絶対パス>` と日付で回す。手順2・3の `fetch_feeds.py` に `--paid` を付ける。curate-news の中の `recent_urls.py`・`recent_topics.py` は実行環境の TZ で今日を決めるので、`TZ=Asia/Tokyo` を付けて回す（UTC のまま 0〜9時 JST に回すと、戻した前日分が重複除外の窓から外れる）。`--paid` が終了コード3（使えるソースが0件）で止まったら、その読者は失敗として次へ進む（finalize を回さなければ、check の要約で失敗に数えられる）（2026-10-21 時点では「可」のソースが0件なので、#241 の結論が出るまで必ずここで止まる）
3. `python3 .claude/scripts/paid_daily.py finalize --root ROOT_DIR --date YYYY-MM-DD --reader ID [--send]` — 当日の出力を `output/paid/{日付}/{読者 ID}.md` に取り分け、本文を生成し、送る。**既定は dry-run**（送る予定を表示するだけ）。`--send` を付けたときだけ実送信し、成功したら出力を `ROOT_DIR/sent/` に保存する。prepare を通っていない・その後にプロファイルが変わった・当日の出力が無い・その日の分を送信済み、のどれかなら送らずに非0で終わる。前回の送信中の印が残っているときも送らない。`ROOT_DIR/footer.json` が無い・空・形式が違うときも送らずに非0で終わる（dry-run は警告を出してフッタ無しの本文で続ける）

全員を回したら:

4. `--send` で回したなら、`ROOT_DIR` の `sent/` を（送信中の印も含めて）private repo に commit・push する（次の run の重複除外と二重送信の防止に使う。push しないと翌日の run から見えない）
5. `python3 .claude/scripts/paid_daily.py check --root ROOT_DIR --date YYYY-MM-DD --text "<公開 repo に書く予定の文>"` — 公開 repo の作業ツリーが clean か、run の起点から HEAD までに `_posts/` への commit が増えていないかを確かめ（Pages は commit からビルドされるので、ここに増えていなければ Pages にも出ない）、公開してよい要約（件数と成否だけ）を表示する。`--text` は要約の書式と完全一致するときだけ通す。非0なら公開 repo に何も書かない

status issue などの公開 repo に書くのは check が表示した要約だけにする。失敗した読者の ID と理由は端末（と `output/paid/{日付}/run.json`）にしか出さない。この run の後に reflect-and-improve を回すときも、証拠として見出し・URL・プロファイルの内容を引用せず、件数と成否で書く。
